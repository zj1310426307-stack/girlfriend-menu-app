# LoveOS V3 渐进式迁移计划

## 原则

- 旧功能、URL、认证、WebSocket 协议和数据全部保留。
- 先建立契约和观测，再迁移内部实现。
- 复用现有成熟依赖；新增依赖必须通过运行时、体积和维护性门槛。
- 每个切片都能独立回滚，不把未验证 PoC 放进生产路径。

## 阶段

### V3-0 审计与护栏

- 固化 HTTP/WS 路由快照、Alembic head、表清单和包体基线。
- 生成 OpenAPI 3.1 工件并验证稳定性。
- 扩展 import-linter，保护 API → Service → Repository 和纯游戏边界。

### V3-1 启动与前端边界

- 新增 `/api/bootstrap` 聚合服务和 response schema。
- 小程序优先调用 bootstrap；404/网络兼容场景回退旧接口。
- 把 `api/index.js` 拆为 transport + 领域模块，旧命名导出继续存在。
- 统一路由常量，为分包迁移消除散落字符串。

### V3-2 游戏插件与 AI 策略

- 在 `games/core` 增加不可变插件描述和注册表。
- 先注册已使用统一引擎的斗地主、斗兽棋、象棋。
- 为飞行棋、五子棋提供 adapter，不重写规则。
- 增加 AI 策略注册、预算和耗时元数据；旧类继续可导入。
- 路由从硬编码分发逐步迁移到注册表。

### V3-3 分包与图片

- 保留 5 个 TabBar 页和必要下单页在主包。
- 游戏详情、后台、情侣二级页移动到独立分包；兼容入口只做受测导航。
- 复用 Pillow 生成受限尺寸的 WebP/缩略图；旧 URL 返回不变。
- CDN 只通过已有 S3 公共基地址配置。

### V3-4 数据库目标模式

- 生成 `database/v3-schema.sql` 可读快照。
- 不压扁 12 个既有 migration。
- 对可能重叠的 `game_states`/`game_sessions` 做读写追踪和数据对账。
- 只有安全回填与回滚方案通过后才新增非破坏 migration。

### V3-5 验证与清理

- 后端 API、Service、Repository、游戏、数据库测试全绿。
- 前端构建、契约测试和微信开发者工具页面验收全绿。
- 本地、staging、真机性能分开报告。
- 只有引用扫描、构建、测试、运行时验收一致确认无引用时才删除文件。

## 框架决策

| 候选 | 当前决策 | 重新评估条件 |
| --- | --- | --- |
| Taro `subPackages` | 采用 | 路由护栏完成后实施 |
| FastAPI OpenAPI | 采用 | 立即纳入契约 |
| Hey API | 延后采用 | 前端 TS 迁移且 Taro transport adapter 成熟 |
| Phaser | PoC/延后 | 真机、体积、触控、后台恢复、许可证全部通过 |
| Colyseus | 不采用 | 出现独立游戏集群和第二运行时的明确业务收益 |
| Pillow WebP | 采用 | 复用当前依赖，不破坏原图 |

## 回滚

- Git 基线：本地 `backup/v2-before-refactor` 指向 `641c0d6`。
- 每个迁移切片保持旧入口；回滚时切换 adapter 即可，不回滚生产数据。
- 新数据库变更必须具备 Alembic downgrade 或明确的前向修复策略。
- 分包发布前保留路由清单；失败时恢复 `app.config.js` 和旧页面路径。

## 完成定义

文档中的“完成”只在自动测试、构建、数据库升级、API 兼容、微信开发者工具和可重复性能证据全部满足后成立。真机未测的指标必须标记为待验收，不能用本地结果代替。
