# V2.8 回滚手册

## 触发条件

- 新设备无法建立会话或旧设备认领大面积失败；
- 订单提交、管理接单或评价主流程不可用；
- 迁移后数据数量异常；
- 对象存储持续失败且影响菜品维护；
- 实时游戏异常消耗后端资源。

## 应用回滚

1. 在 Render 选择上一个已验证部署并执行 Rollback。
2. 微信小程序不要发布有问题的 RC；若已发布，使用微信公众平台版本回退能力恢复上一个审核版本。
3. 保持数据库不降级，旧应用需要兼容新增可空字段；先验证旧应用对新 schema 可正常读写。
4. 检查 `/api/health`、最近订单和管理登录。

## 数据库回滚

优先采用“应用回滚、数据库向前兼容”，不要直接降生产 schema。V2.8 migration 的 downgrade 会删除 `customers`、订单状态事件、房间会话元数据和新增订单时间字段，可能丢失升级后产生的数据，因此只允许在：

1. 已暂停写入；
2. 已生成并验证当前备份；
3. 确认升级后没有需要保留的新数据；
4. 已在临时库演练；

全部满足时执行：

```powershell
cd backend
alembic downgrade 20260809_08
```

如已有升级后数据，使用备份恢复或编写前向修复 migration，不做盲目 downgrade。

## 对象存储回退

生产环境不得回退到 Render 本地 `uploads/` 作为长期方案。S3 故障时保留原 `image_url`，暂停上传/编辑图片；点菜、订单和游戏继续运行。修复存储配置后再恢复上传。

## 回滚后核对

- 核对 `orders`、`order_items`、`reviews`、`favorite_dishes` 行数；
- 随机检查最近 10 个订单明细与状态；
- 验证管理员与普通用户权限隔离；
- 记录故障时间、版本、数据库 revision、恢复动作和验证结果。
