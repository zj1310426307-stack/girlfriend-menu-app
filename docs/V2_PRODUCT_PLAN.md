# 情侣智能厨房管家 V2.0 产品与架构方案

> 基线：`girlfriend-menu-app` 1.0.19。本文是目标方案与分阶段计划，不代表这些能力已经上线。

## 1. V2.0 的目标

V2.0 不把项目改造成餐厅 ERP，而是把现有完整闭环升级为更可靠、更快、更有情侣专属感的“情侣智能厨房管家”。

三个衡量目标：

1. 女朋友打开小程序后，5 秒内能找到想吃的菜或再次点一份常点菜单。
2. 新订单、状态和评价只能由订单所属设备访问，管理端除外。
3. 点菜、管理和一起玩各有清晰入口，小游戏不再挤占点菜主任务。

非目标：

- 不做餐厅支付、排队、桌号、复杂库存和多商户。
- 不在第一阶段接入大模型；先用真实历史数据完成可解释推荐。
- 不一次性推翻 Taro、FastAPI 或现有数据表。
- 不把单机/双人骰子与订单业务强耦合。

## 2. 对 1.0.19 的代码级结论

### 已经做得好的部分

- API 调用集中在 `miniprogram/src/api/`，没有散落到每个页面直接请求。
- 点菜、订单、状态、历史和评价已经形成完整闭环。
- 菜品使用软下架，订单明细保存菜名和价格快照，历史数据不会随菜单修改而损坏。
- 管理订单 WebSocket 已经具备心跳和 3 秒重连。
- SQLite/PostgreSQL 双环境、CI、Pytest 和微信开发者工具冒烟脚本已经存在。

### 需要修复的真实问题

| 等级 | 问题 | 当前证据 | 影响 |
| --- | --- | --- | --- |
| P0 | 订单详情与评价没有归属校验 | `GET /api/orders/{id}`、评价接口为公共路由 | 可枚举订单号访问或评价 |
| P0 | 邀请码硬编码在小程序 | `miniprogram/src/utils/invite.js` | 只能当体验门槛，不能当安全凭据 |
| P1 | 旧购物车可提交已下架菜品 | `crud.create_order()` 查询菜品时未过滤 `is_active` | 管理端下架后仍可能被点到 |
| P1 | 时间没有统一时区语义 | 后端使用无时区 `datetime.now`，前端直接截字符串 | Render UTC 时间可能显示成错误本地时间 |
| P1 | 双人骰子断线不重连 | `diceSocket.js` 关闭后只更新离线状态 | 切后台或弱网会直接丢房间 |
| P1 | 实时房间只在单进程内存 | `DiceRoomManager.rooms` | 服务重启或多实例时房间消失 |
| P1 | 本地上传不持久 | `storage.py` 仅写 `backend/uploads` | Render 重部署后图片可能丢失 |
| P1 | 管理订单全量读取 | `crud.list_orders()` 无分页 | 订单增长后加载和渲染变慢 |
| P1 | “评分最高菜品”口径不准确 | 统计页把整单评分计给订单内每道菜 | 不能证明某一道菜单独获得该评分 |
| P2 | 管理 token 固定且无过期时间 | token 由环境变量确定性哈希得到 | 泄漏后只能轮换密钥使其失效 |
| P2 | 管理鉴权守卫在多个页面重复 | 多个 `admin-*` 页面重复 token/401 跳转 | 后续容易出现不一致 |
| P2 | 首页职责过多 | 首页同时渲染菜单、转盘、管理和两种骰子 | 点菜主任务被稀释 |

## 6. 安全身份方案

推荐使用“设备客户令牌”，而不是给每个订单单独保存一个难以管理的明文 token。

### 新增 customers 表

```text
customers
├── id                  VARCHAR(100) PK
├── token_hash          VARCHAR(64) UNIQUE NOT NULL
├── display_name        VARCHAR(50)
├── dietary_notes       TEXT
├── spicy_preference    SMALLINT
├── created_at          TIMESTAMPTZ
└── updated_at          TIMESTAMPTZ
```

### 新设备流程

1. 小程序首次通过邀请码后调用 `POST /api/customers/session`。
2. 后端生成不可预测的 `customer_id` 和 32 字节随机 token。
3. 数据库只保存 token 哈希，小程序本地保存原 token。
4. 后续下单不再信任请求体中的 `customer_id`，而是从 Bearer token 得到当前客户。

### 旧设备兼容

1. 若本地已有 `gf_customer_id` 但没有新 token，调用一次 `POST /api/customers/claim-legacy`。
2. 旧的高熵 `customer_id` 只用于一次性认领；认领后生成客户 token。
3. 同一个旧标识只能被认领一次。
4. 旧订单不删除、不重建，继续通过已有 `orders.customer_id` 关联。

### 权限规则

- `GET /api/orders/me`：只返回 token 所属客户订单。
- `GET /api/orders/{id}`：客户必须拥有订单；管理 token 可查看全部。
- `POST /api/orders/{id}/review`：客户必须拥有订单且订单已完成。
- 公开 URL 不再携带 `customer_id`。
- 邀请码继续作为产品入口，但文档和代码不把它称为安全认证。

管理 token 改为带签发时间和过期时间的签名 token，建议 12 小时过期；修改 `ADMIN_SECRET` 可整体撤销。

## 7. 数据库升级

### 1.0.20 必需

- 新增 `customers`。
- `orders.customer_id` 增加到 `customers.id` 的逻辑关联；先保留 nullable 兼容旧订单。
- 新增 `orders.status_updated_at`。
- 新增 `order_status_events`，记录状态、修改时间和操作者类型。
- 所有新时间使用带时区 UTC，前端统一转为 Asia/Shanghai 展示。
- 引入 Alembic，先生成一个“当前基线”迁移，再做增量迁移。

### 1.1 建议

```text
favorites
├── customer_id
├── dish_id
└── created_at
UNIQUE(customer_id, dish_id)
```

`dishes` 增加：

- `prep_minutes`：预计制作分钟数。
- `spicy_level`：0～3。
- `tags`：少量结构化标签。
- `sort_order`：管理端手动排序。
- `is_available_today`：今日是否可点；与永久下架 `is_active` 分开。

`orders` 增加：

- `desired_at`：带时区的希望用餐时间，逐步替代自由文本 `desired_time`。
- `source_order_id`：再做一次时记录来源，可选。

### 不建议增加的字段

不要直接在 `dishes` 增加 `dish_order_count`、`last_order_time`、`favorite_score`。这些数据来自订单、评价和收藏，直接冗余会产生同步错误。当前数据量可实时聚合；未来量大时再增加可重建的统计表或物化视图。

### 评分口径

当前评价是“整单评价”，不能准确称为某道菜的单独评分。V2.0 有两个可选方案：

1. 保持整单评价，把统计名称改为“高分订单里最常出现的菜”。
2. 后续新增逐菜评分，再计算真正的“评分最高菜品”。

第一阶段采用方案 1，避免增加评价负担。

## 8. API 设计

### 1.0.20

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/customers/session` | 新建匿名设备会话 |
| POST | `/api/customers/claim-legacy` | 一次性认领旧 `customer_id` |
| GET | `/api/orders/me` | 分页查询我的订单 |
| GET | `/api/orders/{id}` | 按客户或管理员权限查详情 |
| POST | `/api/orders/{id}/review` | 按订单归属提交评价 |
| GET | `/api/admin/orders` | 管理端分页订单 |
| GET | `/api/admin/orders/{id}` | 管理端订单详情 |

旧 `/api/orders/my/{customer_id}` 保留一个发布周期并返回弃用提示，确认所有体验版用户升级后再删除。

分页统一使用游标：

```json
{
  "items": [],
  "next_cursor": "opaque-or-null"
}
```

### 1.1

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/insights/me` | 常点、最近点、收藏和口味摘要 |
| GET | `/api/recommendations/today?mood=comfort` | 可解释的今日推荐 |
| POST | `/api/favorites/{dish_id}` | 收藏菜品 |
| DELETE | `/api/favorites/{dish_id}` | 取消收藏 |
| POST | `/api/orders/{id}/repeat-preview` | 生成再次点单预览并检查可用性 |

推荐接口第一版使用规则，不调用大模型：

- 最近 90 天点单次数。
- 评价意愿与整单评分。
- 今日可用状态。
- 心情到标签的明确映射。
- 避免连续多次重复同一菜。

响应必须带 `reason`，例如“最近点过 4 次，而且你说下次还想吃”。

## 9. 后端结构演进

当前 `main.py + crud.py` 对 1.0.19 足够，但继续增长后应渐进拆分：

```text
backend/
├── app/
│   ├── core/config.py
│   ├── core/security.py
│   ├── db/models/
│   ├── api/dishes.py
│   ├── api/orders.py
│   ├── api/admin.py
│   ├── api/games.py
│   ├── services/order_service.py
│   ├── services/recommendation_service.py
│   └── repositories/
├── alembic/
└── main.py
```

执行原则：每次只迁移一个业务域，旧导入路径在同一版本内保持兼容；不要先创建大量空目录再搬运所有代码。

配置集中到单个 Settings 对象：数据库、API 域名、管理密钥、对象存储和环境名称都从环境变量读取，并在启动时校验生产必填项。

## 10. 图片存储

保持现有 `POST /api/upload/image` 契约，替换后端内部存储适配器，避免管理端页面同步重写。

```text
StorageProvider
├── LocalStorageProvider      # 本地开发
└── ObjectStorageProvider     # 生产
```

生产上传流程：

1. 管理端继续上传 jpg/jpeg/png/webp，限制 5MB。
2. 后端校验扩展名、MIME 和真实图片内容。
3. 对图片重新编码或去除元数据。
4. 上传对象存储并返回稳定 HTTPS URL。
5. `dishes.image_url` 继续保存 URL，已有测试数据不受影响。

对象存储最终选择应根据可访问域名、费用和微信合法域名要求单独确认，不在核心代码中绑定某一家 SDK。

## 11. WebSocket 稳定性

### 管理订单

现有 3 秒重连可以保留，但改为指数退避并增加随机抖动。每次重新收到 `ready` 后必须重新拉取一次订单列表，确保断线期间事件不会遗漏。

### 双人骰子

- 客户端增加自动重连和明确的“正在回到房间”状态。
- 服务端断线后保留玩家席位 60 秒，不立即重置整局。
- 房间增加最后活动时间和 15 分钟 TTL。
- 同一玩家重连时用临时 `room_session_token` 恢复席位。
- 单实例私人使用可继续内存房间；需要多实例时再迁移 Redis，不把高频临时状态写入 PostgreSQL。
- 骰子结果目前由客户端提交，第一版明确为娱乐模式；若需要防作弊，必须改为服务端随机并签名结果。

## 15. 决策结论

V2.0 应先解决订单归属、下架菜品、时区、迁移和断线问题，再重做导航和视觉。最近常点、再做一次和收藏比 AI 更早产生价值；AI、天气和复杂厨房 ERP 必须等真实使用数据证明需要后再进入范围。
