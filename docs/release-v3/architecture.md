# LoveOS V3 生产架构与取舍

## 微信身份链路

```text
微信小程序
  -> wx.login 获取一次性 code
  -> POST /api/customers/wechat-session
  -> 后端调用固定 HTTPS code2Session
  -> wx_users(app_id, openid, unionid?)
  -> customers（稳定业务身份）
  -> customer_sessions（可撤销、多设备、90 天默认 TTL）
```

首次新用户仍需验证 `CUSTOMER_INVITE_CODE`。已有 bearer 的存量用户会把微信身份绑定到当前 `Customer`，不会创建第二份订单、积分、情侣数据或游戏历史。绑定完成后，新手机只需微信身份即可恢复同一用户，并签发独立设备会话；旧手机会话不会被无故注销。

为避免小程序与后端分阶段发布时把全新用户挡在入口外，客户端只在微信登录能力不存在或暂不可用时回退现有 `/api/customers/recover`：无 HTTP 状态的网络失败，或 404、405、501、503。邀请码错误、微信 code 错误、身份冲突和限流等 400、401、409、429 响应不会降级，必须把真实错误反馈给用户。该兼容门只保证旧入口可继续使用，不代表微信身份链路已经通过线上验收。

code2Session 响应必须是对象，`errcode` 必须可解析，`openid` 必须是非空字符串，可选 `unionid` 也必须是字符串；畸形上游响应统一映射为安全的 503，不把解析异常或上游内容泄露为应用 500。已保存 bearer 被服务端拒绝时，首页会清理过期入口状态并重新启动身份恢复；微信已绑定用户优先静默恢复，其他用户回到邀请码验证。

## 数据模型

Alembic head `20260817_14` 新增：

- `wx_users`：一条微信身份绑定一个 `customers.id`；`(app_id, openid)` 和 `customer_id` 唯一。
- `admin_accounts`：数据库管理账号，只保存 scrypt verifier。
- `admin_auth_events`：只保存账号名、结果和时间，不含密码、邀请码、token、IP 或请求体。

配置驱动的管理密码轮换只有在密码、管理邀请码和账号启用状态全部验证成功后才写入数据库；任何失败审计的提交都不能顺带改变密码 verifier。

没有新增第二套 `login_sessions`，因为现有 `customer_sessions` 已经完整承担多设备、过期、撤销和轮换职责。没有新增 `couple_bindings`，因为当前产品的情侣业务数据已经由稳定 `customer_id` 归属，尚无经过产品定义的配对/解绑状态机；提前建表会制造无所有者语义。

## 首页与性能

`GET /api/bootstrap` 在不删除旧接口的前提下一次返回：

- 菜单与推荐排序输入；
- 恋爱值；
- 今日任务；
- 最近订单。

小程序仍保留旧五请求降级路径。菜单命中 Taro 本地缓存时无需网络；图片继续使用现有 WebP 多尺寸和长缓存；游戏与后台继续位于分包。

首页采用“本地先画、后台更新”的启动策略。有效客户会话存在时，React 首帧同步读取该客户最近 24 小时的 bootstrap 快照；快照严格记录 `customerId`，账号不匹配、超时或结构损坏时一律不使用，清理客户会话时同时清理私有首页快照。没有完整快照但存在最近 7 天的公共菜单缓存时，先展示菜品推荐，再补齐恋爱值、任务和订单。网络刷新由单一请求锁拥有，缓存内容保留在页面上，只显示轻量同步提示；无缓存时先绘制首页操作区和骨架，不再用整页等待文案挡住首屏。

菜单、订单、游戏和情侣页也采用同一条 local-first 边界，快照有效期分别为 24 小时、1 小时、1 小时和 6 小时。快照按 `customerId` 隔离，结构不完整或超时即失效；每页只有一个刷新请求拥有写状态的权利，页面回显不会与旧请求竞争。菜单公共数据与个人收藏分开保存，服务端仍是收藏、订单、房间和情侣数据的最终准则。同一次小程序会话中，菜单、订单、游戏和情侣页的成功刷新冷却分别为 2 分钟、30 秒、1 分钟和 2 分钟；失败会立即释放冷却，用户手动重试可强制刷新。

普通 GET 的默认等待预算收紧为 15 秒、最多重试 1 次；首页 bootstrap 采用 12 秒且不重试。只有旧后端明确返回 404、405、501，或 bootstrap 结构不兼容时，才展开旧五接口读取；网络超时和临时服务失败保留本地内容并提示重试，不再向刚唤醒的免费实例同时发送五个请求。写操作继续保留 45 秒预算，避免弱网上传或提交订单被过早中断。Unsplash 种子图在列表端按卡片实际用途请求 480/640 像素、质量 72，并继续使用原生懒加载，减少解码与下行流量；自有上传图片 URL 不被客户端改写。

bootstrap 服务端记录五个读取阶段与总耗时，但不记录 `customerId`、token、请求体或返回数据。该日志用于隔离 staging 判断慢点来自菜品、收藏排序、恋爱值、任务还是最近订单，不改变 API 响应。

微信构建启用 `lazyCodeLoading: requiredComponents`。详情、购物车、订单详情、通知和个人资料保持原 URL，但移入按页面加载的分包；用户启动时不再下载和解析这五个非首屏页面。图片组件继续使用原生懒加载，避免缓存首屏被图片请求再次阻塞。

首页的“今日任务”和“最近订单”摘要承担行动入口职责：分别直达任务页和具体订单详情；无订单时引导到菜单。任务全部完成时显示完成态，不复用某条已完成任务伪装成下一项。

## 订单受理与附属动作

订单行和菜品快照提交成功后即成为下单接口的权威结果。积分、共同记忆、管理员通知和实时广播属于提交后的产品附属动作；其中任一动作失败都不得把已经存在的订单伪装成 HTTP 500。

服务层会区分首次创建与幂等回放。积分、首次用餐记忆和新订单通知使用现有业务唯一来源进行补偿；实时广播只在首次创建时发送。每个附属动作独立回滚失败会话并记录包含 effect、order_id、created、compensable 的结构化错误，不记录订单备注、邀请码或 token。路由只负责鉴权和响应模型，不再拥有这段业务编排。

当前实现解决顺序重试、普通网络重放和并发幂等键插入的错误外泄；它不宣称替代事务 outbox。多实例下若要严格保证附属动作最终恰好一次，需要后续引入专用 effect ledger/outbox 和独立消费者。

订单状态更新、撤回和评价遵守同一主结果规则。状态写入会先对订单行加锁，再在锁内比较客户端可选的 `expected_status`、验证迁移并追加审计事件。新版管理端总是发送页面看到的原状态；字段在滚动兼容期保持可选。目标状态已经成立时可作为幂等回放，用于补偿完成积分、首次做饭记忆和按原事件日期归属的每日任务；其他原状态不匹配返回 409，不执行写入或附属动作。

撤回不再把上一条撤回审计当作新的正向历史，而是寻找最近一次把订单推进到当前状态的非撤回事件。携带原状态的重复请求返回冲突并刷新；旧客户端没有前置条件时，紧邻撤回重试返回当前结果，避免网络重放把状态再次翻转。

评价以订单 ID 作为自然幂等键：相同评分、意愿和评论的重试返回原评价，不同内容返回 409。五星积分、评价任务和管理员评价通知可以顺序补偿；广播只在首次评价时尽力发送。状态通知因为同一订单允许多个不同状态事件，当前只在真实变化时写入，不在回放中补偿；严格事件级去重留给带事件 ID 的 outbox。

## 客户端状态所有权

收藏写操作按菜品串行，订单详情加载按页面串行；轮询失败保留最后一次权威快照。活跃订单、已完成和暂时做不了使用不同标题、评价提示和终态说明。管理订单页把筛选草稿、已应用查询、分页游标、读取代次和写操作锁分开，防止旧读取覆盖刚完成的状态修改。

## 部署形态

Render 已在服务前提供托管 TLS 和边缘反向代理，所以本项目继续使用单一 Uvicorn 应用进程，不在同一容器中重复部署 Nginx。多 worker 会让进程内 WebSocket 连接和后台定时任务重复执行；在完成 Redis 强制化与独立 worker 拆分前，不盲目增加 worker 数量。

`production` / `staging` 属于托管 schema 环境：Uvicorn 生命周期不执行 `create_all` 或六组参考数据种子。三个 Blueprint 全部固定为 `plan: free`，并统一由 `python serve.py` 在一个 Python 进程内完成数据库准备与 Uvicorn 启动，不再连续启动 Alembic、release 和 Uvicorn 三个进程。

免费唤醒先用一条查询同时读取 Alembic head 与六组参考数据的有界计数。head 为 `20260817_14` 且参考数据完整时，跳过 Alembic 导入和六组种子；只有首次部署、schema 漂移或参考数据不完整时才迁移、修复并再次验证。本地开发仍保留自动建表和幂等种子，减少开发门槛。

免费实例的平台代理休眠无法由应用代码消除，因此当前策略是“减少醒来后的工作 + 复访本地先显 + 避免请求风暴”。现有服务位于 Singapore，而已记录的数据库位于 Oregon；`render.production-oregon.yaml` 定义一个同样免费的、手动创建的 Oregon 新服务候选。是否创建、切换 Origin 和停用旧服务必须等隔离 staging 与真机证据通过后单独确认，但不进入付费方案。
