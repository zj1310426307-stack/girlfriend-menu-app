# LoveOS V3 产品审查与优化优先级

审查日期：2026-08-20；staging 隔离补充：2026-08-21
审查范围：微信小程序核心入口、身份恢复、首页决策链路、菜单收藏、订单受理与详情、管理端操作、发布状态与线上只读证据。

## 产品定位

LoveOS 的核心任务不是堆叠功能，而是让两个人更快完成三件事：决定今天吃什么、跟踪点菜单、把共同互动沉淀为轻量的情侣记忆。游戏和成长系统服务于留存，但不能阻塞点菜主流程或增加首次进入成本。

当前五个一级入口的职责合理：

- 首页：帮助用户快速做出今天的选择。
- 菜单：浏览、筛选和加入清单。
- 点菜单：跟踪订单、评价和再次点单。
- 一起玩：集中承载游戏，不挤占首页首屏。
- 我们：承载成长、任务、记录和管理入口。

## 审查结论

### P0：线上前后端版本不一致

2026-08-20 只读核验结果：

- 生产 `/api/health` 返回 200。
- 生产 OpenAPI 版本为 `2.11.0`。
- 生产没有 `POST /api/customers/wechat-session`。
- 生产没有 `GET /api/bootstrap`。
- 生产 `/api/ready` 仍为旧结构，没有 V3 微信登录就绪状态。

因此，服务存活不等于 V3 已部署。`3.0.0` 开发版已经上传，但当前不具备设置体验版并宣称端到端可用的证据。

### P0：staging 不能借用生产环境完成“伪验收”

进入托管验收前核对发现，原 `.env.staging` 仍指向生产 API；如果直接构建，真机看到的是生产 V2.11 后端，既不隔离数据，也不能证明 V3 已部署。本轮已把这个风险改为失败关闭：

- 新增 `render.staging.yaml`，服务名独立、`APP_ENV=staging`、`autoDeploy=false`，微信登录默认关闭。
- `.env.staging` 不再预填生产地址；只有独立服务和数据库完成隔离核对后才允许写入 HTTPS Origin。
- 新增 `build:weapp:staging`，未配置地址或复用生产 Origin 时构建直接失败。
- 发布配置和小程序架构契约同时检查以上边界，避免后续误回退。

2026-08-21 外部核对仍未越过认证边界：Render 浏览器没有登录，GitHub CLI 凭据失效，已连接的 GitHub 应用也没有该仓库权限；本机没有 Neon/Render/微信密钥环境变量。因此尚未创建云资源、迁移数据库、部署代码或生成 staging 真机二维码，不能把本地隔离门写成 hosted 验收完成。

### P0：全新用户存在发布窗口锁死风险

原实现只在微信 session 返回 503 或无 HTTP 状态时降级。面对仍在线的 V2.11 后端，接口会返回 404；全新用户输入正确邀请码也无法继续。

本轮已把兼容门补齐为：只在无 HTTP 状态、404、405、501、503 时回退旧 `/api/customers/recover`。400、401、409、429 不降级，避免掩盖输入错误、身份冲突和限流。

### P1：首页摘要缺少行动闭环

“今日任务”和“最近订单”此前只跳到泛化一级页；任务全部完成时还会把第一条已完成任务显示成“下一项”。本轮已改为：

- 今日任务直达任务页。
- 最近订单直达对应订单详情。
- 无订单时直接引导到菜单。
- 全部任务完成时显示明确完成态。
- 订单摘要使用面向用户的进度文案。

### P1：发布资料发生状态漂移

部分 V3 文档仍写“未上传微信代码”，与 `3.0.0` 已上传为开发版本的事实冲突。本轮已统一为“开发版本已上传、体验版无完成证据、后端 V3 未部署”。

### P1：认证失败不能改变已验证状态

后续安全审查发现，配置驱动的管理密码轮换原本会在管理邀请码校验前修改 ORM 对象；失败审计提交时可能顺带落库新 verifier。本轮已把轮换写入延后到密码、邀请码和账号状态全部通过之后，并增加错误邀请码不改变数据库密码的回归测试。

微信 code2Session 现在会严格验证响应结构，畸形 JSON 统一转换为安全 503。首页 bearer 被服务端拒绝后会重新进入身份恢复流程，不再停留在已清除 token 的伪登录页面。

### P0：已受理订单不能被附属动作伪装成失败

后续核心链路审查发现，订单会先提交数据库，再创建积分、共同记忆、管理员通知和实时广播。原链路中任一附属动作抛错，客户端都可能收到 500，但订单其实已经存在；用户因此可能误以为没有下单。

本轮把下单编排收回服务层，并明确“订单提交”是权威结果：

- 新建与幂等回放会被内部区分，外部响应格式不变。
- 已提交订单的附属动作失败只记录结构化错误，不再把 201 改成 500。
- 可去重的积分、首次用餐记忆和新订单通知会在同一幂等标识重试时补偿。
- 新订单实时广播只在首次创建时发送，普通重试不重复广播。
- 并发命中相同幂等标识时会恢复已存在订单，不泄漏数据库唯一约束错误。

当前无迁移方案能保证顺序重试安全；若未来要求多实例并发下“附属动作绝不丢、绝不重复”，仍应增加事务 outbox 或专用 effect ledger，而不是把通知表的不同业务事件粗暴设为全局唯一。

### P1：核心状态反馈与操作安全不足

本轮继续收紧了实际使用中的误触和状态漂移：

- 收藏操作增加菜品级同步锁和处理中反馈，慢网络下连续点击不会并发写入。
- 订单详情的首次加载、页面回显、轮询和重试共用单请求所有权，旧请求不会与新请求抢状态。
- 自动轮询短暂失败时保留已有订单，不把可用页面替换成整页错误。
- 订单标题、终态副标题和评价提示按真实状态变化；“暂时做不了”不再承诺“做好后可评价”。
- “再看看菜单”现在真正进入菜单，而不是返回首页。
- 管理端区分筛选草稿与已应用条件，不再边输入边查询并重连；分页追加、旧响应覆盖、重复加载更多均有保护。
- “已完成”和“暂时做不了”在提交前给出各自的结果确认；管理登录过期和并发冲突都有明确恢复路径。

### P0：状态更新、撤回和评价也必须如实确认

第二轮审查发现，下单受理修复后，订单状态、撤回和评价仍保留了同类事务窗口：主状态或评价已经提交，随后积分、任务、通知、记忆或实时广播失败时，接口仍可能返回 500。撤回在响应丢失后直接重试，甚至可能把刚撤回的状态再次翻转。

本轮把这三条写路径统一到服务层的可靠性规则：

- 状态写入先锁定订单行，在同一锁内比较页面看到的 `expected_status`、校验合法迁移并写审计事件。
- 新版管理端始终发送卡片上的原状态；字段暂时保持可选，保障新旧小程序和后端分阶段发布。
- 状态或评价主记录提交后立即形成响应快照；每个附属动作独立失败、独立回滚会话并记录结构化错误，不再反向制造虚假失败。
- 完成积分、首次做饭记忆和按事件日期归属的每日任务可以在同目标状态回放时补偿；实时广播只在真实状态变化或首次评价时发送。
- 状态通知只在真实变化时发送。当前没有事件级通知去重键，失败时宁可依赖页面轮询恢复权威状态，也不在 HTTP 回放中冒险重复通知。
- 相同内容的评价以订单为自然幂等键，重试返回原评价并补齐可去重的积分、任务和管理员通知；不同内容仍返回 409。
- 撤回按“最近一次把订单推进到当前状态的非撤回事件”寻找上一步；新版请求的原状态不匹配时返回 409，旧版无前置条件的紧邻重试按幂等结果处理，避免反向翻转。

这轮解决的是主流程如实确认和单实例/顺序重试安全，不宣称获得跨实例 exactly-once。状态事件级通知和跨进程并发补偿仍应由后续 transactional outbox 或 effect ledger 承担。

### P2：功能密度高于当前验证密度

项目已经包含多个完整游戏和成长模块，但 V3 当前最缺的是微信登录、点菜主流程和真机网络的外部验收，而不是新增功能。在完成体验版验证前，暂停新增游戏和大规模视觉重构，把工程与验收资源集中到身份、菜单、订单、图片和 WebSocket 冒烟。

## 下一阶段优先级

1. 恢复 GitHub、Render 和 Neon 的受控登录，确认当前混合工作区中哪些文件属于 staging 发布候选。
2. 提交确认范围内的 V3 候选分支，部署隔离 staging，并把空白数据库迁移到 `20260817_14`。
3. 确认 `/api/ready` 的微信登录状态为 ready，再验证新用户、存量绑定和换机恢复。
4. 用真机完成点菜、订单状态、评价、撤回、图片、五个一级入口和 WebSocket 冒烟。
5. 新旧管理端完成滚动升级后，把 `expected_status` 从兼容可选提升为强制前置条件；需要跨实例严格补偿时再引入 outbox/effect ledger。
6. 取得“体验版显示 3.0.0”的权威证据后，再讨论提交审核。

## 产品验收指标

当前不虚构线上转化率。体验版阶段至少记录以下不含隐私明文的结果：

- 新用户邀请码登录成功/失败及固定错误类型。
- 存量用户绑定后 `customer_id` 是否保持不变。
- 换机恢复是否回到同一业务身份。
- 首页从打开到可操作的冷启动、热启动耗时。
- 从首页到加入菜品、提交订单所需步骤与成功结果。
- 同一幂等标识重试是否返回同一订单，且不重复通知或实时广播。
- 订单状态、评价、再次点单闭环是否完成。
- 两个管理端基于同一旧状态操作时，后到请求是否得到 409 且不会追加错误审计或副作用。
- 状态、撤回或评价的通知/广播模拟失败时，主结果是否仍如实成功并可从权威页面恢复。
- 慢网络连续收藏、订单自动刷新和管理端加载更多是否保持单一权威状态。
- WebSocket 重连是否恢复到权威快照。

这些指标先用于小规模体验验收；任何正式埋点方案都应另行定义数据最小化、保留周期和隐私披露。

## 2026-08-23 首页启动产品化优化

- 有有效登录态的复访用户在 React 首帧同步恢复自己的首页快照，不再等待 hosted API 才看到内容。
- 快照按客户隔离、24 小时过期，退出或 401 清会话时一并清理；公共菜品缓存最多保留 7 天用于升级和弱网首帧，不缓存 bearer。
- 网络刷新改为后台同步并有单一请求锁；已有内容不会被 loading 清空，无缓存时先显示完整首页操作区和骨架。
- 微信启用按需组件注入；详情、购物车、订单详情、通知和个人资料移出启动主包，公开路由保持不变。
- 生产构建与完整小程序 CI 通过。首页单轮完成时主包由 488,022 bytes 降至 458,780 bytes，减少 29,242 bytes（6.0%）；该数字已被下一轮四页优化后的最终结果替代。
- 以上证明工程路径和包体预算通过，不替代隔离 staging 上的微信真机冷/热启动各 10 次 P95 验收。

## 2026-08-23 全入口与托管启动优化

- 菜单、订单、游戏、情侣四个一级页加入按账号隔离、分 TTL 的 local-first 快照；页面回显时只后台同步，不再每次切页清空内容等待网络。
- 每页只有一个刷新请求拥有状态写入权；菜单把公共菜品与个人收藏拆开，订单/房间/情侣数据仍以服务端为最终准则。
- 普通 GET 收紧为 15 秒、最多重试一次；bootstrap 为 12 秒且不重试，失败立即进入旧接口降级；写请求保持 45 秒。
- Unsplash 列表图按用途请求 480/640 像素和质量 72，自有上传 URL 不改写；所有列表仍使用原生懒加载。
- production/staging 的 Uvicorn 生命周期不自动迁移或种子；所有 Blueprint 已改为 `plan: free` 和单进程 `python serve.py`，不再保留 Starter 或 pre-deploy 候选。
- 普通免费唤醒只用一条查询检查 Alembic head 与参考数据完整性；只有首次部署、schema 漂移或种子缺失时才迁移和修复。隔离 SQLite 第二次快路径约 5.0ms。
- 首页超时不会再展开旧五接口请求风暴；Tab 成功刷新增加会话内冷却，失败和手动重试可立即重新请求。
- `render.production-oregon.yaml` 保留为免费同区新服务候选，未同步云端、未切流、未产生新增费用。
- 后端全量 228 tests、Ruff、compileall、Import Linter（128 files / 408 dependencies / 5 contracts）、发布配置、密钥扫描（480 files）、隔离免费启动冒烟均通过。
- 小程序生产构建和完整 CI 通过。最终主包 467,041 bytes，分包 420,844 bytes，总包 887,885 bytes；仍比 488,022 bytes 基线小 20,981 bytes（4.30%）。
- 本地 bootstrap p95 为 21.270 ms；这只证明本地代码预算，hosted 冷启动和微信真机可交互 P95 仍待隔离 staging 验收。
